Modules injected into the page

DashboardRemovedStill loaded
Some integrations add JavaScript to every page through Home Assistant's extra_module_url rather than registering a Lovelace resource, so trim_resources never sees them. With trim_extra_modules on, one is removed only when it is also a registered resource that this dashboard already dropped — the decision the resource trim already made, applied to the channel it was leaking through. Still loaded is the half worth reading: those are modules this app deliberately will not judge, because nothing here knows what an icon pack or a frontend patcher does. If a panel has quietly lost a behaviour, it is either in Removed or it is not this app's doing.

Payload is the first entity block this connection received, with the number of entities in it — the dump a dashboard cannot render without, and the part this app shrinks. The entity count is shown so the byte figure can be checked: a small payload against a large Entities allowlist means a partial first block, not a tiny dashboard. Ready in is from the websocket opening to that block being written out. On the wire is how long that write took to be accepted by the network stack.

Read these as diagnostics, not as a benchmark. Ready in is dominated by how long the frontend takes to get around to subscribing — auth handshake, JavaScript parse — rather than by moving the payload; a LAN wall panel here took 671 ms for 1.5 KB while a phone on 5G took 207 ms for 215 KB. On the wire means handed to the kernel socket buffer, not received by the device: a 215 KB payload "drained" in 6 ms over cellular, which is far faster than any real transfer. Neither number is a round trip, and neither should be quoted as a speed.

Resource tuning

Every resource below is installed in Home Assistant and referenced by no dashboard this app serves — so no panel is receiving it. That means one of two things, and the app cannot tell which:
  • Genuinely unused — the honest fix is to uninstall it, not to have a proxy hide it on every page load.
  • A resident module that registers no card and is named by no config, but runs on load: an idle timer, a camera pop-up, a heartbeat. Dropping one of those is invisible — the dashboard renders normally and only the behaviour stops. Pin it.
Pinning writes to resources_always_forward and is applied immediately — the resource scan re-runs, with no restart.

How clients reach this

OriginRouteHostnameConnectionsShare
Each band is one connection path, read left to right: where the client was, how the request arrived, and which name it dialled. Band thickness is the number of connections. Counted for every connection, including ones that have since closed — unlike the live list above. Origin is whether the client's address is inside RFC1918 or outside it; a device on your own LAN that connects through an external hostname leaves the network and comes back, so it correctly reads as internet. Route is how the request arrived — direct to the port, through a reverse proxy, through cloudflare, or over Supervisor ingress. Hostname is the name the client dialled, which is usually the clearest statement of which entry point it used. This is reporting only: every signal except the peer address is a request header, so none of it is trustworthy enough to make access decisions with.
